注解的常见误区

六个坑

  • 忘了写 @Retention(RUNTIME)：反射永远返回 null，编译不报错、运行也不报错，而默认策略恰恰就是 CLASS。
  • 以为注解能继承：注解类型不能写 extends，编译直接报「对于 @interfaces, 不允许 'extends'」，也不能声明类型参数。子类同样读不到父类方法上的注解，只有类注解配合 @Inherited 才向子类传递。
  • 元素写成 default null：编译直接失败，报「元素值必须为常量表达式」。
  • @Target 写窄了：贴到不允许的位置是编译错误「批注接口不适用于此类型的声明」，这个还算好查。
  • 以为注解能区分重载：两个方法只有注解不同，签名仍然相同，重复定义会编译报错。
  • 把反射拿到的注解对象当普通对象存起来、当 Map 键、或用 == 比较——它只是代理实例，比较请用 equals。

什么时候该用

适合「元信息和处理逻辑天然分离」的场景：权限声明、日志埋点、校验规则、序列化字段名、路由映射，以及第三方类或 JDK 类也需要被框架识别的时候——注解不需要改被标注的代码， @Bean 能接管 String 这种类就是为此存在。

不适合拿来做普通业务分支（那是 if 的活），不适合只表达意图（那是注释的活），尤其不适合「注解一漏就完全静默」的关键逻辑：读不到注解时没有任何提示，排查成本很高。

一句话

注解是贴在声明上的结构化标签； @Retention 决定标签能否活到运行期，反射或字节码工具负责把标签读出来，框架负责按标签做事。写注解时你在声明，真正执行逻辑的永远在别处。
