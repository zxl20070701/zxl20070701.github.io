工具调用（Tool Calling）

工具调用是 Agent 从“会说”走向“会做”的关键。模型负责判断什么时候需要工具、调用哪个工具、传入什么参数；系统负责真正执行工具，并把结果返回给模型继续推理。

为什么需要工具？

大模型擅长语言理解和推理，但它本身并不天然拥有实时数据、文件系统、数据库、浏览器或代码运行环境。工具调用就是给模型接上这些外部能力。

常见工具类型

  • 搜索工具：查询网页、文档、知识库。
  • 文件工具：读取、创建、修改、移动文件。
  • 代码工具：运行脚本、执行测试、分析报错。
  • 数据库工具：查询数据、写入记录、生成报表。
  • 业务工具：创建订单、发送消息、审批流程等。

工具定义

一个工具通常需要说明名称、用途、入参结构和返回结构。入参最好使用明确的 Schema，这样模型更容易生成稳定、可验证的参数。 

{
  "name": "read_file",
  "description": "读取指定路径的文本文件",
  "parameters": {
    "type": "object",
    "properties": {
      "path": {
        "type": "string",
        "description": "文件路径"
      }
    },
    "required": ["path"]
  }
}

调用流程

  1. 模型分析任务，发现需要外部信息或执行能力。
  2. 模型选择合适的工具，并生成结构化参数。
  3. 运行时校验参数，执行工具。
  4. 工具返回结果或错误信息。
  5. 模型根据观察结果继续回答或发起下一次调用。

设计要点

工具粒度

工具不要过大，也不要过碎。过大的工具会让模型难以控制细节；过碎的工具会让调用链变长，增加错误概率。通常让一个工具完成一个清晰动作即可。

参数约束

参数要尽量结构化，避免让模型传入一整段自然语言再由工具二次解析。比如用 start_date、end_date、status，比传入“查一下最近完成的任务”更稳定。

错误可读

工具失败时要返回模型能理解的错误原因，例如“文件不存在”“权限不足”“参数缺少 id”。模糊的错误会让 Agent 很难自我修复。

权限边界

涉及删除、支付、发送消息、修改生产数据等高风险动作时，应加入确认、审批或沙箱机制，避免模型直接造成不可逆影响。

一个判断原则

如果某件事需要最新信息、外部状态、精确计算或真实执行，就优先考虑工具；如果只是解释概念、总结已给材料或生成草稿，模型直接完成通常就够了。

工具调用的三种错误

选错工具

常见原因是工具名称相似、描述太泛，或者一次暴露太多工具。解决方法是减少可选工具数量，并在 description 里写清“什么时候用”和“什么时候不用”。

参数错误

常见原因是参数类型太松、字段名不贴近业务、缺少枚举和范围限制。能用 Schema 约束的地方，不要只靠自然语言说明。

结果误读

工具返回的信息太长、太杂或缺少摘要时，模型容易抓错重点。返回值应突出 status、summary、items、next_actions 这类决策字段。

工具描述模板 

工具名称：search_docs
用途：在项目文档中检索资料。
适合使用：用户询问项目已有约定、接口说明、配置含义时。
不适合使用：用户要求修改文件或执行命令时。
输入：query、limit、scope
输出：匹配片段、来源路径、更新时间
失败：没有结果时返回空列表，不要编造答案

工具治理

当工具越来越多时，需要治理机制：按任务动态选择工具、按权限过滤工具、记录调用日志、统计工具失败率。否则 Agent 会从“能力增强”变成“选择困难”。
