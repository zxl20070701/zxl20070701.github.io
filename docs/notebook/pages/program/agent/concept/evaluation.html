Agent 评估与观测

Agent 评估不只看模型回答是否通顺，更要看它是否正确完成任务、是否调用了合适工具、是否遵守权限边界，以及失败时能不能解释原因并恢复。

为什么评估 Agent 更难？

普通文本生成通常只有输入和输出，而 Agent 中间还有计划、工具调用、环境状态和多轮反馈。同一个任务可能有多条完成路径，因此评估既要看最终结果，也要看执行过程。

评估维度

任务成功率

判断 Agent 是否真的完成了用户目标。例如代码是否通过测试、文件是否生成、数据是否查询正确。

工具使用质量

观察 Agent 是否选择了合适工具、参数是否正确、是否避免了不必要的重复调用。

过程稳定性

同一个任务多次运行时，结果是否稳定；遇到错误时，是否能根据错误信息修复，而不是陷入循环。

安全合规

检查是否越权访问、泄露敏感信息、执行高风险操作，是否在必要时请求人工确认。

常见评估方法

  • 人工评审：适合早期探索和高价值任务。
  • 规则断言：用测试、脚本、Schema 校验等方式判断结果是否合格。
  • 回放测试：保存真实任务轨迹，框架或模型升级后重新运行对比。
  • 对照实验：比较不同提示词、模型、工具设计下的成功率和成本。
  • LLM-as-judge：让模型辅助评分，但重要场景需要结合人工或规则校验。

观测数据

生产环境中的 Agent 应尽量记录可追踪的执行轨迹，包括用户输入、计划摘要、工具调用、工具返回、错误信息、耗时、token 消耗和最终输出。

Trace

Trace 记录一次完整任务的调用链，帮助定位 Agent 在哪一步判断错误、工具失败或上下文不足。

Metrics

Metrics 关注整体趋势，例如任务成功率、平均耗时、平均调用次数、重试次数、人工介入比例等。

Logs

Logs 用于保留具体错误和关键事件，方便排查线上问题。

一个简单评估表

项目 问题
结果 最终交付物是否满足用户目标？
过程 是否有多余调用、错误循环或遗漏步骤？
证据 关键结论是否有来源、测试或工具结果支撑？
安全 是否遵守权限、隐私和人工确认规则？

离线评估数据集

做 Agent 评估最好沉淀一批真实任务样本。每条样本包含输入、期望结果、允许使用的工具、禁止行为和评分标准。这样每次修改 prompt、模型或工具后，都可以回放对比。 

{
  "id": "case-001",
  "input": "帮我找出订单 A1024 为什么没有发货",
  "allowed_tools": ["get_order", "get_shipping_log"],
  "expected": {
    "must_find": ["订单已支付", "缺少收货地址"],
    "must_not_do": ["直接取消订单"]
  },
  "rubric": {
    "task_success": 5,
    "tool_use": 3,
    "safety": 2
  }
}

线上评估闭环

  1. 记录真实失败案例。
  2. 把失败案例整理成可回放测试。
  3. 定位失败来自检索、工具、模型还是业务规则。
  4. 修改对应模块。
  5. 回放旧用例，避免修一个坏一个。

不要只看平均分

Agent 任务通常长尾很多，平均分可能掩盖高风险失败。更实用的做法是按任务类型、工具类型、风险等级分别统计成功率。
