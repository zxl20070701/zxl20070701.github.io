编程 Agent 实战

编程 Agent 是 Agent 技术最典型的应用之一。它需要理解需求、阅读代码、制定修改方案、编辑文件、运行测试、根据错误迭代，最后交付变更说明。

基本工作流

  1. 理解需求：明确要修复什么、不要动什么。
  2. 读取上下文：查看目录结构、相关文件、测试和文档。
  3. 定位修改点：找到最小改动范围。
  4. 实施修改：遵循项目已有风格。
  5. 验证结果：运行测试、构建或手动检查。
  6. 总结交付：说明改了什么、如何验证、剩余风险。

文件阅读策略

不要一开始读完整仓库。更好的方式是先看文件列表，再用搜索定位关键词，然后阅读相关文件和邻近测试。 

1. 查看目录：了解项目类型和模块边界
2. 搜索关键词：找到功能入口、错误信息、组件名
3. 阅读实现：理解当前代码风格和数据流
4. 阅读测试：确认已有行为和边界条件
5. 再修改：避免凭猜测改代码

修改原则

  • 优先最小改动，避免顺手重构。
  • 沿用项目已有抽象和命名。
  • 不要覆盖用户未提交的改动。
  • 共享逻辑改动要补测试。
  • 失败时根据报错定位，不要盲目大改。

验证策略

验证要和改动风险匹配。文案修改可以做简单检查；组件改动需要页面或截图验证；核心逻辑改动应运行单元测试；构建链路改动要跑完整构建。

改动类型 建议验证
文档/笔记 菜单链接、构建、拼写检查
UI 组件 本地页面、截图、响应式检查
业务逻辑 单元测试、边界用例
接口改动 集成测试、请求响应检查

常见失败模式

  • 没读够上下文，改错位置。
  • 只修 happy path，漏掉边界条件。
  • 测试失败后不看报错，直接猜。
  • 把无关格式化混入业务改动。
  • 生成代码可运行，但不符合项目风格。

一个实用 Prompt 

请像资深工程师一样处理这个代码任务。
要求：
- 先阅读相关文件，确认项目现有模式。
- 只做完成任务所需的最小改动。
- 不要覆盖我已有的未提交改动。
- 修改后运行合适的测试或构建。
- 最后说明改动文件、验证结果和剩余风险。
