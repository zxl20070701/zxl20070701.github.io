工具设计实战

Agent 的能力上限常常不是模型决定的，而是工具决定的。工具设计得清楚，模型就容易正确调用；工具边界模糊，再强的模型也会频繁传错参数或做错动作。

一个好工具的标准

  • 名称能表达动作，例如 search_docs、read_file、create_ticket。
  • 描述说明何时使用，而不只是重复工具名。
  • 参数结构明确，尽量少用自由文本。
  • 返回结果简洁，包含下一步需要的信息。
  • 错误信息可恢复，告诉模型应该怎么修正。

工具粒度怎么拆？

工具粒度可以按“一个业务动作”拆分。比如订单系统里，get_order、update_address、cancel_order 就比一个万能的 operate_order 更容易控制。

设计 问题 更好的方式
do_anything(command) 权限不可控，参数不可验证 拆成多个明确工具
query(sql) 可能产生危险查询 提供受限查询接口
update(data) 不知道更新对象和影响范围 指定 id、字段、预期版本

参数设计

参数越接近业务结构，Agent 越稳定。日期、状态、枚举、数量、id 等都应该显式声明。 

{
  "name": "search_orders",
  "description": "按条件查询订单。适合用户想查看订单状态、筛选异常订单时使用。",
  "parameters": {
    "type": "object",
    "properties": {
      "status": {
        "type": "string",
        "enum": ["pending", "paid", "shipped", "cancelled"]
      },
      "start_date": {
        "type": "string",
        "description": "开始日期，格式 YYYY-MM-DD"
      },
      "end_date": {
        "type": "string",
        "description": "结束日期，格式 YYYY-MM-DD"
      },
      "limit": {
        "type": "number",
        "default": 20
      }
    },
    "required": ["status"]
  }
}

返回值设计

返回值不要把数据库整行都塞给模型，只返回本次决策需要的信息。必要时返回 summary + items 的结构。 

{
  "summary": "找到 3 个待发货订单",
  "items": [
    {
      "order_id": "A1024",
      "status": "paid",
      "amount": 199,
      "created_at": "2026-08-28"
    }
  ],
  "next_actions": ["查看详情", "标记异常", "创建发货单"]
}

幂等性

写入类工具最好支持 idempotency_key。Agent 遇到网络超时或中断时可能重试，如果没有幂等键，可能重复创建订单、重复发送邮件或重复扣费。

权限与确认

可以把工具分成三类：

  • 只读工具：一般可自动执行。
  • 可回滚写入工具：执行前说明影响范围，必要时确认。
  • 不可回滚高风险工具：必须人工确认，并记录审批人和审批时间。

调试清单

  • 模型是否总能选对工具？如果不能，工具描述可能不清楚。
  • 模型是否经常传错参数？如果是，Schema 可能太松。
  • 工具结果是否太长？如果是，需要摘要和分页。
  • 失败后模型是否知道怎么修？如果不知道，错误信息需要改写。
  • 重试是否会产生副作用？如果会，需要幂等设计。
