RAG 工程落地

RAG 不是“把文档丢进向量库”这么简单。真正可用的 RAG 需要处理文档解析、切分、索引、召回、重排、引用、更新和评估，每一步都会影响最终回答质量。

基本链路

  1. 文档采集：收集 PDF、网页、Markdown、数据库记录等资料。
  2. 文本解析：提取正文、标题、表格、代码块和元数据。
  3. 清洗切分：去掉噪声，并按语义边界切块。
  4. 向量索引：为切块生成 embedding，写入向量库。
  5. 查询改写：把用户问题改写成更适合检索的查询。
  6. 召回重排：先召回候选片段，再用重排模型或规则过滤。
  7. 生成回答：把高质量片段交给模型，要求基于资料回答。
  8. 引用溯源：输出来源，方便用户检查。

切分策略

切分太大，检索不精准；切分太小，片段缺少上下文。常见做法是按标题层级、段落、代码块或表格边界切分，再设置少量 overlap。

资料类型 建议切分方式
技术文档 按标题层级切分，保留标题路径
API 文档 按接口切分，保留参数表和示例
代码仓库 按文件、函数、类切分，保留路径
PDF 报告 按章节和页码切分，保留页码来源

元数据很重要

每个 chunk 应带上来源、标题路径、更新时间、权限、文档类型等元数据。没有元数据，后续很难做过滤、引用和增量更新。

召回优化

  • 关键词召回：适合精确术语、函数名、错误码。
  • 向量召回：适合语义相近但表达不同的问题。
  • 混合召回：同时使用关键词和向量，通常更稳。
  • 重排：对候选片段重新排序，提高前几条的相关性。
  • 查询改写：把口语化问题转成更明确的搜索问题。

生成阶段约束

生成回答时，应要求模型优先依据检索片段回答；资料不足时明确说明不足，而不是编造。重要答案应带来源引用。 

请仅根据给定资料回答问题。
如果资料不足，请回答“资料不足”，并说明还需要什么信息。
回答中需要列出使用到的来源标题或文件路径。

评估指标

  • Recall：正确资料是否被召回。
  • Precision：召回资料里有多少是真的相关。
  • Faithfulness：回答是否忠于资料。
  • Answer Correctness：最终答案是否解决问题。
  • Citation Accuracy：引用来源是否真的支持结论。

常见问题排查

  • 答非所问：优先检查召回结果，而不是先改 prompt。
  • 引用错乱：检查 chunk 元数据和引用模板。
  • 回答太泛：提高重排质量，减少无关上下文。
  • 资料过期：为索引建立增量更新和过期策略。
  • 权限泄露：检索阶段必须按用户权限过滤。
