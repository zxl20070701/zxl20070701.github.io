多 Agent 协作模式

多 Agent 的目标不是“让系统看起来更高级”，而是把复杂任务拆给不同角色，降低单个 Agent 的上下文压力，并让专业能力可以复用。

常见模式

Supervisor 模式

一个主 Agent 负责理解目标、分配任务、整合结果；多个子 Agent 负责具体领域工作。它适合复杂但可以拆分的任务，例如产品调研、代码改造、长文档分析。

Debate 模式

多个 Agent 从不同角度提出方案或质疑，最后由裁判 Agent 或人工选择。它适合高不确定性的分析任务，但成本较高。

Pipeline 模式

每个 Agent 负责流水线中的一个阶段，例如“抽取信息 → 校验 → 生成报告 → 审核”。它适合流程稳定的生产任务。

Swarm 模式

多个 Agent 根据状态动态接力，谁更适合处理当前问题就交给谁。它灵活，但调试和收敛更难。

角色设计

子 Agent 的角色要具体，最好包含职责、输入、输出和禁止事项。 

你是代码审查 Agent。
职责：
- 找出 bug、边界条件、测试缺口。
- 只输出问题和证据，不重写代码。

输入：
- 变更 diff
- 相关文件片段

输出：
- 严重程度
- 文件和行号
- 问题原因
- 建议修复方向

上下文传递

不要把完整对话全部转发给每个子 Agent。更好的做法是传递任务摘要、相关资料、明确边界和预期输出。

结果整合

主 Agent 不能机械拼接子 Agent 的输出，而要做冲突解决、去重、优先级排序和最终验收。多 Agent 失败最常见的原因就是“分出去容易，收回来困难”。

适合使用多 Agent 的情况

  • 任务天然可拆分，例如调研、设计、实现、测试。
  • 不同子任务需要不同专业知识。
  • 上下文太大，单 Agent 难以同时处理所有材料。
  • 需要并行探索多个方案。

不适合的情况

  • 任务很小，拆分成本高于收益。
  • 多个子任务会修改同一文件同一逻辑。
  • 结果必须高度一致，且没有明确整合规则。
  • 预算有限，不能承受多倍模型调用成本。
