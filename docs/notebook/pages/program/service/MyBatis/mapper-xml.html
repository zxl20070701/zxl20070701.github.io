映射文件与增删改查

接口和 XML 是怎么对上的

没有实现类，也没有注解扫描的魔法，绑定靠四条硬规则同时成立：

  • XML 的 namespace 等于接口的全限定名。
  • 语句的 id 等于方法名。
  • 语句的参数类型能接住方法参数，结果类型能接住返回值。
  • 这个 XML（或这个接口）已经在 <mappers> 里注册过。

任意一条不满足，运行时都是 Invalid bound statement (not found)，不是编译错误，所以最容易在「改了个方法名」之后炸。

参数怎么进 SQL 

User selectById(Long id);                                  // 单个简单参数
User selectByNameAndStatus(String name, Integer status);   // 多个参数：必须 @Param
int updateEmail(@Param("id") Long id, @Param("email") String email);
List<User> selectByUser(User user);                       // 一个对象

<!-- 单个参数：名字随便写，#{id} / #{value} / #{aaa} 都行 -->
<select id="selectById" resultType="User">
    SELECT * FROM sys_user WHERE id = #{id}
</select>

<!-- 多个参数：不写 @Param 就只能用 arg0 / param1 这种位置名 -->
<select id="selectByNameAndStatus" resultType="User">
    SELECT * FROM sys_user WHERE user_name = #{name} AND status = #{status}
</select>

<!-- 对象：按属性名取 -->
<select id="selectByUser" resultType="User">
    SELECT * FROM sys_user
    WHERE user_name = #{userName} AND status = #{status}
</select>

单个参数时名字随意，是 MyBatis 的宽容之处；一旦有第二个参数，它就把所有参数塞进一个 Map，你能用的名字只剩 arg0、arg1 和 param1、param2。忘了 @Param 的报错非常直白，照抄原文就能定位： 

org.apache.ibatis.binding.BindingException:
Parameter 'keyword' not found.
Available parameters are [arg1, arg0, param1, param2]

看到 Available parameters 里出现 arg0 这种名字，就说明方法上少写了 @Param。规则很简单：参数超过一个，全部加 @Param，别去记位置名。

集合参数 

List<User> selectByIds(List<Long> ids);

<select id="selectByIds" resultType="User">
    SELECT id, user_name FROM sys_user
    WHERE id IN
    <foreach collection="list" item="item" open="(" separator="," close=")">
        #{item}
    </foreach>
</select>

只有一个集合参数时，MyBatis 会把它单独包一层，默认名字是 list（数组则是 array），所以 collection 写 list 而不是方法参数名。加了 @Param("ids") 之后就改成 collection="ids"，和普通多参数一致。写成方法参数名会报 Parameter 'ids' not found 之类的错。

语句标签的常用属性

  • parameterType：可以完全不写。MyBatis 从接口方法签名就能推断参数类型，写错反而会覆盖成错误类型。
  • resultType / resultMap：二选一。列名与属性名能对上（含下划线转驼峰）用 resultType；有嵌套对象、列名要改名、需要类型转换时用 resultMap。
  • useGeneratedKeys + keyProperty：自增主键回填，keyProperty 是实体里的字段名，不是列名。
  • timeout：这条语句的超时秒数，覆盖全局的 defaultStatementTimeout。
  • useCache / flushCache：是否走二级缓存、是否执行前清缓存。默认 select 的 useCache 是 true、flushCache 是 false，增删改的 flushCache 是 true——这就是「一改就查得到新数据」的原因。
  • statementType：STATEMENT / PREPARED / CALLABLE。默认 PREPARED，用 #{} 就是预编译；CALLABLE 用于存储过程。

返回什么类型都行 

<!-- 基本类型：统计 -->
<select id="count" resultType="long">
    SELECT COUNT(*) FROM sys_user
</select>

<!-- 一个对象 -->
<select id="selectById" resultType="User">
    SELECT id, user_name FROM sys_user WHERE id = #{id}
</select>

<!-- 对象列表：resultType 写元素类型 -->
<select id="selectAll" resultType="User">
    SELECT id, user_name FROM sys_user
</select>

<!-- 无实体时用 Map，key 是列名 -->
<select id="statByStatus" resultType="map">
    SELECT status, COUNT(*) AS total FROM sys_user GROUP BY status
</select>

resultType 永远写「一个元素」的类型，集合交给接口返回值声明，MyBatis 自己知道要装 List。resultType="map" 返回的 Map 里 key 是列名原样（大小写跟随数据库），下游按字符串取值，一旦表结构改名就会悄悄变成 null。

增删改返回的是行数 

int rows = userMapper.deleteById(1L);
if (rows == 0) {
    throw new IllegalStateException("记录不存在");
}

返回 0 不代表出错，只代表条件没匹配到任何行。用它做乐观锁是最常见的用法：UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?，返回 0 就说明版本已被别人改过。

批量插入的两种做法

第一种是拼一条多值 INSERT，一次往返： 

<insert id="insertBatch">
    INSERT INTO sys_user (user_name, email, status)
    VALUES
    <foreach collection="list" item="u" separator=",">
        (#{u.userName}, #{u.email}, #{u.status})
    </foreach>
</insert>

第二种是开 BATCH 执行器，把 N 条普通 insert 攒成一批发送，代码不改、SQL 不改，只换 Session 的创建方式： 

try (SqlSession session = factory.openSession(ExecutorType.BATCH, false)) {
    UserMapper mapper = session.getMapper(UserMapper.class);
    for (User user : users) {
        mapper.insert(user);
    }
    session.flushStatements();   // 真正发送
    session.commit();
}

BATCH 模式下每句的返回值不再即时可得，得看 flushStatements 的结果；而且一旦中途某条失败，整批的报错位置会很模糊。几万条以内的批量，多值 INSERT 更好排查；上更大数量级，配合 rewriteBatchedStatements=true 的 JDBC 参数，BATCH 才有明显优势。

分页只能自己写 

<select id="selectPage" resultType="User">
    SELECT id, user_name FROM sys_user
    ORDER BY id
    LIMIT #{limit} OFFSET #{offset}
</select>

int pageNo = 1, pageSize = 10;
List<User> rows = userMapper.selectPage(pageSize, (pageNo - 1) * pageSize);
long total = userMapper.count();

MyBatis 不做物理分页，只有 RowBounds 这种「把结果全查出来再在内存里截断」的逻辑分页，数据量大时等于自己造一次 OOM。生产上要么像上面手写 LIMIT，要么用 PageHelper 这种拦截器插件——它在 Executor 层拦下查询，自动拼 LIMIT 并执行一次 count，代价是 SQL 由插件改写，出问题时要看插件拼出来的最终语句。

update 的两个陷阱 

<!-- 危险：没传的字段会被写成 null -->
<update id="update">
    UPDATE sys_user
    SET user_name = #{userName}, email = #{email}, status = #{status}
    WHERE id = #{id}
</update>

<!-- 安全：只更新非空字段 -->
<update id="updateSelective">
    UPDATE sys_user
    <set>
        <if test="userName != null">user_name = #{userName},</if>
        <if test="email != null">email = #{email},</if>
        <if test="status != null">status = #{status},</if>
    </set>
    WHERE id = #{id}
</update>

第一种是全字段覆盖：如果前端只传了 id 和 email，user_name 就会被覆盖成 null，而数据库里完全看不出是谁干的。第二种是选择性更新，也是 tk-mybatis、MyBatis-Plus 里 updateById 的默认行为。

另一个陷阱是「更新了但没生效」：语句确实执行了，只是字段值没变。多数是参数名对不上（对象里叫 userName，SQL 写了 #{username}），而 MyBatis 对对象属性取不到值时不报错，直接给 null。

注解写法和 XML 写法 

public interface AnnoMapper {

    @Select("SELECT id, user_name FROM sys_user WHERE id = #{id}")
    @Results(id = "userMap", value = {
            @Result(column = "id", property = "id", id = true),
            @Result(column = "user_name", property = "userName")
    })
    User findById(Long id);

    @Insert("INSERT INTO sys_user (user_name, email, status) VALUES (#{userName}, #{email}, #{status})")
    @Options(useGeneratedKeys = true, keyProperty = "id")
    int save(User user);

    @Update("UPDATE sys_user SET email = #{email} WHERE id = #{id}")
    int updateEmail(@Param("id") Long id, @Param("email") String email);

    @Delete("DELETE FROM sys_user WHERE id = #{id}")
    int remove(Long id);
}

简单固定的 SQL 用注解更清爽，省掉一个 XML 和一次文件跳转；一旦涉及动态条件、复用片段、resultMap 嵌套，注解会退化成一长串字符串拼接，可读性远不如 XML。实践中的折中是：单表 CRUD 用注解，复杂查询放 XML，同一个接口两种混用是允许的（只要不重名）。

注意用注解的接口必须在配置里注册，<mapper class="..."> 或 <package> 都行。只把接口放在包里、不注册，session.getMapper 会报 Type interface ... is not known to the MapperRegistry。
