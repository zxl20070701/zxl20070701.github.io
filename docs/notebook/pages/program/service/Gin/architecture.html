项目分层架构

为什么需要分层

接口少的时候所有逻辑写在 handler 里没问题，但接口一多就会乱：换数据库要改 handler、加缓存要改 handler、统一错误格式要改每个 handler。分层的目的是让每种变化只碰一层。

四层结构

典型的 Go Web 项目分四层，依赖方向单向向下：

  • handler 层：只跟 HTTP 打交道，解析请求、校验参数、返回响应
  • service 层：只写业务规则，不 import gin，不认识 *gin.Context
  • repository 层：只跟数据源打交道，从内存或数据库读写
  • model 层：纯数据结构定义，谁都能用

依赖注入

在 main 里手动组装依赖，而不是在每个包里 new 全局单例： 

userRepo := repository.NewInMemoryUserRepo()
userSvc := service.NewUserService(userRepo)
userH := handler.NewUserHandler(userSvc)

这样换数据库实现时只改一行，service 和 handler 不用动。repository 用 interface 定义能力，service 依赖接口而不是具体实现。

统一响应格式

所有接口返回统一壳，前端只写一个分支处理： 

type Result struct {
    Code int         `json:"code"`
    Msg  string      `json:"msg"`
    Data interface{} `json:"data"`
}

func OK(c *gin.Context, data interface{}) {
    c.JSON(200, Result{Code: 0, Msg: "ok", Data: data})
}

func Fail(c *gin.Context, status int, msg string) {
    c.JSON(status, Result{Code: 1, Msg: msg, Data: nil})
}

全局异常兜底

写一个 Recovery 中间件兜底 panic，返回统一格式的 500，而不是暴露堆栈： 

func Recovery() gin.HandlerFunc {
    return func(c *gin.Context) {
        defer func() {
            if r := recover(); r != nil {
                c.AbortWithStatusJSON(500, gin.H{
                    "code": 500, "msg": "internal server error",
                })
            }
        }()
        c.Next()
    }
}
