探针与自动扩缩容

本篇介绍两个让服务「更健壮、更省资源」的能力： 探针（Probe） 用来判断容器的健康状态， HPA 用来根据负载自动调整副本数。

三种探针

探针 作用 失败后果
startupProbe 判断容器是否启动完成 超过阈值则重启容器（启动期间禁用其它探针）
readinessProbe 判断容器是否准备好接收流量 从 Service 的后端列表中移除
livenessProbe 判断容器是否还活着 重启容器
记忆方式：startup 管启动， readiness 管「能不能接流量」， liveness 管「要不要重启」。

配置探针 

apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello
spec:
  replicas: 1
  selector:
    matchLabels:
      app: hello
  template:
    metadata:
      labels:
        app: hello
    spec:
      containers:
        - name: hello
          image: nginx:alpine
          ports:
            - containerPort: 80
          livenessProbe:
            httpGet:
              path: /
              port: 80
            initialDelaySeconds: 10
            periodSeconds: 10
            timeoutSeconds: 1
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /
              port: 80
            initialDelaySeconds: 3
            periodSeconds: 5

各参数的作用：

  • initialDelaySeconds：容器启动后等待多久才开始探测，避免因为启动慢而误判失败。
  • periodSeconds：多久探测一次。
  • timeoutSeconds：单次探测的超时时间。
  • failureThreshold：连续失败几次才算探测失败，默认 3 次。
  • successThreshold：连续成功几次算成功，默认 1 次（liveness 只能是 1）。

除了 httpGet，还可以使用 exec （在容器内执行命令）、 tcpSocket （检查端口能否连通）和 grpc 探针： 

          livenessProbe:
            exec:
              command:
                - cat
                - /tmp/healthy
            initialDelaySeconds: 5
            periodSeconds: 10

启动探针解决慢启动问题

有些应用启动要花几十秒，如果只靠 livenessProbe，会在启动过程中被误杀。此时用 startupProbe「保护」启动阶段： 

          startupProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 5
            failureThreshold: 30
          livenessProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 10

上面的配置意味着：启动后最多容忍 30 × 5 = 150 秒 的启动时间；一旦启动探针成功，就切换到由 livenessProbe 接管。

水平自动扩缩容（HPA）

HPA 根据 Pod 的 CPU、内存或自定义指标自动调整 Deployment 的副本数。 

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: hello-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: hello
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50

字段含义：

  • minReplicas / maxReplicas：副本数的上下限。
  • averageUtilization：目标 CPU 使用率百分比（相对于 requests 的比例）。

应用后查看状态： 

kubectl apply -f hpa.yaml
kubectl get hpa
kubectl describe hpa hello-hpa

NAME       REFERENCE              TARGETS         MINPODS   MAXPODS   REPLICAS   AGE
hello-hpa   Deployment/hello      0%/50%         2         10        2          30s
HPA 依赖 metrics-server 才能采集到 CPU/内存指标。kind 默认不带 metrics-server，需要额外安装，否则 TARGETS 会一直显示 <unknown> ，HPA 不会生效。

手动压测验证

扩缩容是异步的，触发后需要等待一段时间。可以手动制造负载来观察效果： 

# 进入某个 Pod
kubectl exec -it hello-xxxxx -- sh

# 在容器内循环消耗 CPU
while true; do echo "x"; done

然后观察副本数变化： 

kubectl get pods -w
kubectl get hpa
如果集群没有装 metrics-server，也可以用 kubectl top pods 看资源使用（同样依赖 metrics-server），或者 kubectl top nodes 看节点整体负载。

垂直扩缩容

HPA 调整的是副本数（水平扩缩），VPA（VerticalPodAutoscaler）调整的是单个 Pod 的资源额度（垂直扩缩）。需要注意的是， VPA 触发的调整会导致 Pod 重建 ，在生产环境中要谨慎使用。 

# 查看 VPA（需要安装 VPA 组件）
kubectl get vpa
