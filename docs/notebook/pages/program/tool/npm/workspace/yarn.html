yarn 工作空间

Yarn 从 1.0 开始就原生支持工作空间（Workspaces），也就是常说的 monorepo：一仓库多包。它会自动把各个子包软链接（symlink）到根目录的 node_modules 中，因此只需要执行一次安装命令，就能把所有子包的依赖一次性装好。

基本使用

比如我们现在有一个项目，项目中有两个子项目，大体结构如下： 

- packages
    - pkg1
        - package.json
    - pkg2
        - package.json
- package.json
- yarn.lock

而pkg1和pkg2的项目名称分别是mypkg1和mypkg2。

在根目录的package.json中声明workspaces字段即可，它既支持直接写路径，也支持 glob 通配符： 

{
    "private": true,
    "workspaces": [
        "packages/*"
    ]
}
根包强烈建议加上 "private": true 。工作空间本身就是用来放子包的，不应该被发布，加 private 是一道安全保险。
Yarn 1（classic）中根包的 private: true 是硬性要求；从 Yarn 2 起这个限制被取消，根包可以不是 private。

声明完成后，在根目录执行一次 yarn install 即可。安装完成后目录结构大致如下： 

/package.json
/yarn.lock

/node_modules
/node_modules/cross-env
/node_modules/mypkg1 -> /packages/pkg1

/packages/pkg1/package.json
/packages/pkg2/package.json

注意node_modules 中的软链接用的是 package.json 里的 name 字段，而不是文件夹名字。也就是说，如果 packages/pkg1 的名字叫 mypkg1 ，那链接就是 node_modules/mypkg1 -> /packages/pkg1 ，代码里 require('mypkg1') 引用到的就是它。

引用工作空间包

Yarn 1（classic）

Yarn 1 中直接写普通的版本号范围即可，只要版本对得上就会优先链接本地工作空间： 

{
    "dependencies": {
        "mypkg1": "^1.0.0"
    }
}

Yarn 2+（Berry）

Yarn 2 引入了 workspace: 协议，明确表示“这个依赖必须来自本地工作空间”，写法如下： 

{
    "dependencies": {
        "mypkg1": "workspace:^"
    }
}

其中冒号后面可以是普通版本范围，也可以是 ^ 、 ~ 、 * 这三个特殊符号。它们不会影响本地解析方式（永远只认同名的工作空间包），但会影响发布后写进 npm 仓库的版本范围。假设 mypkg1 当前版本是 3.2.1 ，发布时的转换规则如下：

声明时 发布后
workspace:^3.0.0 ^3.0.0
workspace:^ ^3.2.1
workspace:~ ~3.2.1
workspace:* =3.2.1

常用命令

在单个工作空间中执行命令

Yarn 2+ 使用 yarn workspace 子命令： 

# 在 mypkg1 中添加依赖
yarn workspace mypkg1 add react

# 在 mypkg1 中移除依赖
yarn workspace mypkg1 remove some-package

# 运行 mypkg1 的 build 脚本
yarn workspace mypkg1 run build

Yarn 1 中的写法是 yarn workspace 命令名和参数名（注意中间有空格），比如： 

yarn workspace awesome-package add react react-dom --dev

在所有工作空间中执行命令

Yarn 1 使用 yarn workspaces run ： 

# 在每个工作空间中执行 test 脚本
yarn workspaces run test

# 透传参数，常用于 CI 流程
yarn workspaces run test --ci

Yarn 2+ 使用 yarn workspaces foreach ，功能更强大： 

# 对所有工作空间执行 build
yarn workspaces foreach -A run build

# 并行执行，并实时输出日志
yarn workspaces foreach -Apt run build

# 按拓扑顺序执行（依赖先于依赖方），且只发布非 private 的包
yarn workspaces foreach -A --no-private npm publish --tolerate-republish

yarn workspaces foreach 的常用参数：

参数 说明
-A, --all 对项目中的所有工作空间执行
-R, --recursive 对当前工作空间及其递归依赖执行
-p, --parallel 并行执行
-t, --topological 等依赖执行完后再执行当前工作空间
-j, --jobs 并发任务数上限，也可用 unlimited
--include / --exclude 白名单 / 黑名单，支持 glob
--since 只处理自指定 ref 以来有改动的工作空间
--no-private 跳过 private 的工作空间

查看工作空间 

# 列出所有工作空间
yarn workspaces list

# 列出工作空间之间的依赖关系
yarn workspaces list --verbose

# Yarn 1：查看工作空间依赖树
yarn workspaces info

聚焦安装（focused install）

如果你只想开发其中一个子包，而不想把其他子包都构建一遍，可以使用聚焦安装。Yarn 2+ 的命令是： 

yarn workspaces focus mypkg1

Yarn 1 中对应的写法是进入子包目录后执行： 

cd packages/pkg1
yarn install --focus

聚焦安装会把兄弟依赖从 npm 仓库拉取一份浅安装（而不是链接本地源码），这样就不需要先构建兄弟包了。

全局脚本

普通脚本只能在声明它的工作空间里执行（需要在对应目录下运行），但名字里带冒号（:） 的脚本会被提升为全局脚本，可以在项目任意位置执行： 

{
    "scripts": {
        "build:app": "vite build",
        "build:lib": "tsc -p tsconfig.build.json"
    }
}

# 在根目录直接执行
yarn build:app
如果有两个工作空间定义了同名的全局脚本，它们都不会被提升为全局脚本，此时需要注意重名。

与 Lerna 的关系

Yarn 的工作空间只是提供了底层的“依赖解析 + 软链接”能力，不负责版本管理和发布编排。Lerna、Changesets、Rush 这类工具都是在 Yarn 工作空间之上做更上层的封装。

注意事项

  • 工作空间必须是根目录的子目录，不能引用层级之外的项目；Yarn 1 也不支持嵌套工作空间。
  • Yarn 1 中如果某个工作空间声明的依赖版本和根目录不一致（比如 workspace-a 用的是 1.x，workspace-b 用的是 2.x），那么不一致的那一个会从 npm 仓库安装而不是链接本地包。
  • 发布前务必检查每个子包的依赖是否都写全了。本地测试可能因为根目录已经装过该依赖而通过，但发布后使用者会因为依赖缺失而报错。
  • Yarn 1 可以在 .yarnrc 中通过 workspaces-experimental false 关闭工作空间特性。
