pnpm 工作空间

基本使用

比如我们现在有一个项目，项目中有两个子项目，大体结构如下： 

- packages
    - pkg1
        - package.json
    - pkg2
        - package.json
- package.json
- pnpm-workspace.yaml

其中pnpm-workspace.yaml内容如下： 

packages:
  - 'packages/*'

而pkg1和pkg12的项目名称分别是mypkg1和mypkg2。

主目录下安装：

比如在项目根项目下安装pkg1，只需要： 

    pnpm install mypkg1 -w

子项目下安装：

比如在子项目pkg2下安装pkg1，只需要： 

cd packages/pkg1
pnpm install mypkg1

工作空间配置文件

pnpm 的工作空间必须有一个根目录下的 pnpm-workspace.yaml 文件。它既是工作空间的声明文件，也是 pnpm 的项目级配置文件。

packages 字段

packages 字段决定哪些目录会被纳入工作空间，既可以写具体的子目录，也可以用 glob 通配符，还可以用 ! 排除某些目录： 

packages:
  # 直接子目录下的某个包
  - 'my-app'
  # packages 目录下的所有包
  - 'packages/*'
  # components 目录下的所有包（含多层）
  - 'components/**'
  # 排除测试目录下的包
  - '!**/test/**'
pnpm 只读取 pnpm-workspace.yaml，不读取根 package.json 的 workspaces 字段。 从 v12.7.0 起，如果仓库里只有 workspaces 字段而没有 pnpm-workspace.yaml ，执行 pnpm install 会自动生成一份内容相同的 pnpm-workspace.yaml ；但如果两个地方都写了且内容不一致，pnpm 会打印警告并只认 pnpm-workspace.yaml 。
根包永远属于工作空间，即使 packages 用了自定义的通配符。

packageConfigs 字段

packageConfigs 用来给个别工作空间单独设置 npm 配置（替代以前在各子包下放 .npmrc 的做法）： 

packages:
  - "packages/project-1"
  - "packages/project-2"

packageConfigs:
  "project-1":
    saveExact: true
  "project-2":
    savePrefix: "~"

引用工作空间包

pnpm 默认开启 linkWorkspacePackages 的判断逻辑：只要工作空间里存在与依赖名相同、且版本满足声明范围的包，就会链接本地包而不是从仓库下载。这种行为存在不确定性，所以 pnpm 提供了 workspace: 协议来显式声明： 

{
    "dependencies": {
        "mypkg1": "workspace:^"
    }
}

用了 workspace: 协议后，pnpm 拒绝解析到工作空间之外的任何包。如果本地没有对应版本，安装会直接失败。这在把 linkWorkspacePackages 关掉时尤其有用。

协议后面可以跟：

写法 说明
workspace:* 任意版本，发布时替换为工作空间的实际版本
workspace:~ 发布时替换为 ~实际版本
workspace:^ 发布时替换为 ^实际版本
workspace:^1.0.0 发布时保留原样
workspace:../foo 通过相对路径引用另一个工作空间包
workspace:foo@* 用别名引用，发布时转换为 npm:foo@版本

发布时（无论 pnpm pack 还是 pnpm publish ）， workspace: 协议会被自动替换成普通版本范围。比如各包版本都是 1.5.0 时： 

{
    "dependencies": {
        "foo": "workspace:*",
        "bar": "workspace:~",
        "qar": "workspace:^",
        "zoo": "workspace:^1.5.0"
    }
}

会被转换成： 

{
    "dependencies": {
        "foo": "1.5.0",
        "bar": "~1.5.0",
        "qar": "^1.5.0",
        "zoo": "^1.5.0"
    }
}
这样既能在本地依赖工作空间的源码，又能把包正常发布到仓库，不需要先发一个再发下一个。

版本目录（Catalog）

monorepo 里同一个依赖经常被十几个包引用，版本号散落在各个 package.json 里既难维护又容易冲突。pnpm 的 catalog: 协议可以把版本范围收敛成一份常量： 

packages:
  - 'packages/*'

catalog:
  react: ^18.3.1
  redux: ^5.0.1

然后在各个包中直接引用： 

{
    "dependencies": {
        "react": "catalog:",
        "redux": "catalog:"
    }
}

这等价于直接写 ^18.3.1 。也可以定义多个具名目录，通过 catalog:名称 引用： 

catalog:
  react: ^16.14.0

catalogs:
  react17:
    react: ^17.0.2
  react18:
    react: ^18.2.0

catalog: 协议可以用在 dependencies 、 devDependencies 、 peerDependencies 、 optionalDependencies 以及 pnpm-workspace.yaml 的 overrides 中，发布时同样会被替换成实际版本范围。

常用命令

递归执行命令

-r （ --recursive ）可以对工作空间中的所有包执行命令： 

# 对所有包执行发布
pnpm -r publish

# 对所有包执行测试
pnpm -r test

# 对所有包执行构建
pnpm -r build

# 某个包失败时继续执行其余包
pnpm -r --no-bail test

run 、 exec 、 test 默认按照依赖拓扑顺序执行（依赖先于依赖方），加上 --parallel 可以并行执行，加上 --reverse 可以反向执行。

过滤包

--filter （简写 -F ）可以精确挑选要操作的包： 

# 精确匹配
pnpm --filter mypkg1 test

# 按作用域匹配
pnpm --filter "@myorg/*" test

# 选中包及其所有依赖
pnpm --filter "mypkg1..." test

# 只选中它的依赖
pnpm --filter "mypkg1^..." test

# 选中包以及所有依赖它的包
pnpm --filter "...mypkg1" test

# 按目录 glob 匹配
pnpm --filter "./packages/**" build

# 选中自某个提交以来有改动的包，以及依赖它们的包
pnpm --filter "...[origin/master]" test

# 排除
pnpm --filter=!mypkg1 test

查看信息 

# 列出工作空间中的所有包
pnpm list -r --depth -1

# 查看某个包为什么被安装
pnpm why react

# 查出过期的依赖
pnpm outdated -r

关键配置

配置 默认值 说明
linkWorkspacePackages false 是否自动把工作空间里的包链接为依赖，可选 true / false / deep
includeWorkspaceRoot false 递归执行脚本时是否把根包也算进去
workspaceConcurrency 4 递归执行时最大并发任务数，设为 Infinity 表示不限制
failIfNoMatch false 过滤条件没有匹配到任何包时是否报错
catalogMode manual pnpm add 时是否自动把依赖写入目录，可选 manual / strict / prefer

注意事项

  • pnpm 使用硬链接 + 内容寻址的存储方式，磁盘占用远小于 npm，但如果你手工把 node_modules 整体拷走，会破坏硬链接关系。
  • 如果出现 There are cyclic workspace dependencies 警告，说明工作空间之间存在循环依赖，pnpm 无法保证脚本的执行顺序，需要检查 dependencies 、 optionalDependencies 和 devDependencies 中的声明。
  • pnpm 没有内置的多包版本编排能力，统一发版推荐使用 changesets 或 Rush 。
