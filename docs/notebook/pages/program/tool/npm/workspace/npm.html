npm 工作空间

npm 从 7.0 开始支持工作空间（Workspaces）。它可以在一个顶层根包中管理多个本地文件系统中的包，安装时自动把这些包软链接（symlink）到根目录的 node_modules 中，从而省去手工执行 npm link 的麻烦。

基本使用

比如我们现在有一个项目，项目中有两个子项目，大体结构如下： 

- packages
    - pkg1
        - package.json
    - pkg2
        - package.json
- package.json
- package-lock.json

而pkg1和pkg2的项目名称分别是mypkg1和mypkg2。

在根目录的package.json中声明workspaces字段即可，它既支持直接写路径，也支持 glob 通配符： 

{
    "name": "my-workspaces-powered-project",
    "private": true,
    "workspaces": [
        "./packages/*"
    ]
}

在根目录执行一次 npm install 之后，子包会被软链接到根目录的 node_modules 中： 

- node_modules
    - mypkg1 -> ../packages/pkg1
- package-lock.json
- package.json
- packages
    - pkg1
        - package.json
    - pkg2
        - package.json

链接用的名字来自各子包 package.json 的 name 字段，所以代码里直接 require('mypkg1') 就能引用到 packages/pkg1 。这正是 Node.js 的模块解析机制决定的：任何工作空间都可以按声明的名字被消费。

常用命令

创建工作空间

可以用 npm init 配合 -w 自动创建目录、生成 package.json ，并同步维护根包的 workspaces 配置： 

npm init -w ./packages/pkg1

为工作空间添加依赖

-w （ --workspace ）可以在指定的工作空间上下文中执行安装： 

# 给工作空间 a 添加 registry 上的依赖
npm install abbrev -w a

# 把工作空间 b 作为工作空间 a 的依赖
npm install b -w a

第二条命令中，npm 会识别出 b 是一个工作空间，于是直接软链接而不是去仓库下载，写进 package.json 的是一个普通的版本范围： 

{
    "dependencies": {
        "b": "^1.0.0"
    }
}
npm 目前不支持 pnpm / Yarn Berry 的 workspace: 协议。 写成 "b": "workspace:*" 会直接报错 EUNSUPPORTEDPROTOCOL （Unsupported URL Type "workspace:"）。npm 里请使用 "b": "*" 或 "b": "^1.0.0" 这类普通版本范围。
其他像 uninstall 、 ci 等安装类命令同样会遵循 workspace 配置。

在工作空间上下文中执行脚本

--workspace （或简写 -w ）用于指定单个工作空间， --workspaces 用于指定所有工作空间： 

# 在工作空间 a 中执行 test
npm run test --workspace=a

# 同时在 a 和 b 中执行 test
npm run test --workspace=a --workspace=b

# 在 packages 目录下的所有工作空间中执行 test
npm run test --workspace=packages

# 在所有工作空间中执行 test
npm run test --workspaces

# 跳过没有定义该脚本的工作空间
npm run test --workspaces --if-present

命令的执行顺序与根包 package.json 中 workspaces 数组的书写顺序一致。也就是说： 

{
    "workspaces": ["packages/a", "packages/b"]
}

和 "workspaces": ["packages/b", "packages/a"] 的执行顺序是不一样的。

如果当前目录就在某个工作空间内部，那么 workspace 配置会被隐式设置， prefix 也会指向根工作空间，所以下面两种写法效果相同： 

npm run test --workspace=a

cd packages/a && npm run test

发布工作空间 

# 发布指定工作空间
npm publish --workspace=mypkg1

# 发布多个工作空间
npm publish --workspace=mypkg1 --workspace=mypkg2

# 发布所有工作空间
npm publish --workspaces

默认情况下不会发布根包，如果需要把根包也算进去，加上 --include-workspace-root ： 

npm publish --workspaces --include-workspace-root

查询工作空间依赖

npm query 支持用 CSS 选择器查询依赖树，其中 .workspace 表示工作空间： 

# 列出所有工作空间
npm query ".workspace"

# 列出所有依赖了其他工作空间的工作空间
npm query ".workspace > .workspace"

配置项说明

配置 说明
workspace 指定单个工作空间，可传多次。取值可以是工作空间名、工作空间目录路径，或者父目录路径（会选中该目录下的全部工作空间）
workspaces 置为 true 表示在所有工作空间的上下文中执行命令；显式置为 false 则完全忽略工作空间
include-workspace-root 默认 false。开启后执行命令时会把根包也算进去

注意事项

  • npm 只把工作空间链接进 node_modules ，不做依赖提升（hoisting）优化，磁盘占用会明显大于 pnpm。
  • npm 没有内置的版本编排能力，多包统一发版需要借助 Lerna、Changesets 之类的工具。
  • 根包建议设置 "private": true ，避免误把根包发布到仓库。
  • 如果从 pnpm / Yarn Berry 迁移到 npm，需要把所有 workspace: 协议改成普通版本范围，否则安装会直接失败。
