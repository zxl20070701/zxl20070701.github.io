高效使用经验

前面几篇讲的是"怎么装、怎么配"，这篇讲的是"怎么用得顺手"。内容来自 Claude Code 官方最佳实践和官方团队工程师的实际用法，涵盖 CLAUDE.md 记忆管理、Hooks 自动化、Subagents 并行、验证习惯、权限与上下文管理这几个高频场景。

如果只能 adopt 一条实践，就是给 Claude 一个自我验证的手段——让它能跑起来看看自己写的东西对不对，而不是只靠读代码判断。这一条的收益远大于其他所有技巧。

CLAUDE.md：项目的长期记忆

CLAUDE.md 是 Claude Code 每次启动都会自动读进上下文的文件，用来存放"项目的事实"——技术栈、目录结构、构建命令、代码规范。写好它是所有其他技巧的前提。

该写什么、不该写什么

该写（事实） 不该写（过程）
构建和测试命令（npm run build） 某次 bug 的排查过程
项目结构说明 可以从代码直接推断的内容
不可违反的约定（不要改这个目录） 大段代码片段
外部依赖的坑（这个 API 必须用 v2） 某个函数的逐行解释

进入一个项目时，直接让 Claude 帮你生成初版： 

/init
CLAUDE.md 是每次会话都要花 context 读它的，所以越短越好。当某一段内容从"事实"膨胀成"操作步骤"时（比如"如何新增一个页面"的完整流程），就把它挪进 Skill——Skill 只在被用到时才加载，几乎不占成本。

Hooks：把重复劳动自动化

Hooks 是"确定性的"——不像 CLAUDE.md 只是建议，Hooks 是规则保证一定执行。配置在项目里的 .claude/settings.json（只想自己用就写全局的 ~/.claude/settings.json）。

常用 Hook 事件

事件 触发时机 典型用途
PreToolUse 工具执行前 拦截危险命令、校验路径、自动放行安全操作
PermissionRequest 某次工具调用需要做权限决策时 自动批准测试命令、阻止访问敏感文件
PostToolUse 工具执行成功后 跑格式化、触发 lint、记录文件变更
PreCompact 上下文压缩前 备份对话记录、保留关键决策
SessionStart 会话开始或恢复 注入 git status、加载待办清单
Stop Claude 回答结束时 验证任务是否真的完成、跑测试
SubagentStop 子 Agent 完成时 校验子 Agent 输出
UserPromptSubmit 你提交 prompt 时 注入当前迭代重点、校验请求
Notification Claude Code 需要你注意时 弹系统通知、响铃、发送到手机
SessionEnd 会话结束时 清理临时文件、汇总本次会话记录

示例一：编辑后自动格式化 

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}

matcher 用来过滤触发条件，Write|Edit 表示只在写文件或改文件时触发，支持正则。写成 * 就是所有工具都触发。

Hook 没有"当前被编辑文件"这类环境变量，工具参数是从 stdin 传进来的 JSON，所以要用 jq 之类的工具解析出 tool_input.file_path（记得先装 jq）。

示例二：保护关键文件不被修改

把校验脚本放在项目里，Hook 里用 $CLAUDE_PROJECT_DIR 引用它，保证不管当前工作目录在哪都能正确执行： 

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-files.sh"
          }
        ]
      }
    ]
  }
}

脚本从 stdin 读 JSON，拿到 tool_input.file_path 判断是否在保护目录里，是就 exit 2 阻断操作： 

#!/bin/bash
# .claude/hooks/protect-files.sh
FILE_PATH=$(jq -r '.tool_input.file_path')

case "$FILE_PATH" in
  */migrations/*|*/.env*)
    echo "禁止修改：$FILE_PATH 属于受保护文件"
    exit 2  # exit 2 = 阻断该次工具调用
    ;;
esac
exit 0
Hook 的退出码有明确语义：0 放行、2 阻断并把 stderr 作为理由反馈给 Claude、其他值视为非致命错误只记录日志。

示例三：会话开始时注入 git 状态 

{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "startup",
        "hooks": [
          {
            "type": "command",
            "command": "echo '## 当前分支' && git branch --show-current && echo '## 未提交改动' && git status --short"
          }
        ]
      }
    ]
  }
}

Subagents：并行与隔离

Subagent 是一个独立的 Claude 实例，有自己干净的 context window。它做完任务后只把结论返回给主对话，中间的探索过程不会污染主上下文——你可以把它理解成浏览器标签页。

什么时候该用

场景 信号 收益
研究型任务 理解一件事需要读几十个文件 主对话保持干净，只带回总结而非原始内容
多个独立任务 子任务之间没有依赖关系 并行执行，整体更快
需要无偏视角 做代码审查、不希望受之前对话的影响 子 Agent 不继承主对话的假设和盲区
提交前验证 需要一个第二意见 避免" familiarity 导致的盲区"
判断信号很简单：任务需要读 10 个以上文件，或者包含 3 个以上互不依赖的子任务，就该让子 Agent 上。

内置的三种 Subagent

  • Explore：只读的快速代码搜索，用于调查
  • Plan：先研究代码库再给实现方案
  • general-purpose：通用的复杂多步任务

自定义 Subagent

在 .claude/agents/ 下放 Markdown 文件即可定义一个专属角色： 

---
name: build-validator
description: Runs the test suite and type checks after changes, then reports failures. Use after any code modification to verify nothing broke.
tools: Bash, Read, Grep
model: sonnet
---

You are a build validator. After any code change:

1. Run the project's test suite
2. Run the type checker
3. If either fails, report the exact error output and the most likely cause
4. Do NOT attempt to fix the errors yourself — only report them

几个实用字段：

  • tools：限制这个 Agent 能用哪些工具（比如只给 Bash/Read，天然做到只读）
  • model：给这个 Agent 单独指定模型，比如 model: haiku，干粗活用便宜的模型
  • isolation: worktree：在独立的 git worktree 里跑，适合大批量改动互不干扰

在 Skill 里驱动子 Agent

也可以不手动调，而是在 Skill 正文里直接要求 Claude 派发： 

把这项迁移工作批量执行：启动 10 个并行的子 Agent，每个负责一个目录，
每个 Agent 改完后自己跑端到端测试，最后各自提一个 PR。

验证：让 Claude 能检查自己的产出

这是收益最大的一条实践。三种做法，从轻到重：

1. 给 Claude 启动方式

用 /run 启动你的应用并看到效果，它会从 README、package.json、Makefile 里推断怎么跑。适合"改完想亲眼看看对不对"的场景。

2. 录制启动配方

如果项目需要数据库、env 文件、图形界面这类非标准启动方式，跑一次 /run-skill-generator，它会把"安装命令 + 环境变量 + 启动脚本"记成项目级 Skill 放在 .claude/skills/run-<name>/。之后 /run 就照着这个配方走，不用每次重新摸索。

3. 提交前强制验证

/verify 是内置 Skill，同样会构建你的应用、跑起来、观察实际行为。它不会自动执行，需要你显式调用；项目里可以放一个同名的 verify Skill 把验证步骤写死，这样团队里每个人跑的流程都一致。 

---
name: verify
description: Build and run the app to confirm a change works as intended, without falling back to tests alone.
disable-model-invocation: true
allowed-tools: Bash, Read
---

## 验证步骤

1. 构建项目
2. 启动应用
3. 触发本次改动相关的功能路径
4. 观察实际行为是否符合预期
5. 如果不符合，明确指出偏差，不要修改代码

并行：用多个会话同时干活

Claude Code 原生支持 git worktree 隔离，你可以同时开 3-5 个会话各干各的： 

# 开一个隔离的 worktree 会话
claude --worktree feature-a

# 也可以顺便开一个独立的 tmux 窗口
claude --worktree feature-b --tmux

配合 shell 别名（za、zb、zc 分别跳对应 worktree）+ 终端标签页配色 + 终端通知，就能在多个任务间自由切换而不会搞混。

上下文管理

Claude 的表现会随 context 填满而下降——所以核心心法是主动管理上下文：

  • /clear：清空当前对话重新开始，比硬撑着长对话干净
  • /compact：手动压缩，保留关键决策丢掉冗余细节
  • 把 CLAUDE.md 里膨胀成"操作流程"的内容挪进 Skill
  • 研究型任务交给 Subagent，别让几十个文件的原文都进主上下文
  • 发现方向跑偏就尽早打断纠正，别等它把错误方向做完

提示词写作

一个通用的三段式结构，适用场景比想象中广： 

[需求目标] + [技术栈指定] + [约束条件]

例：创建一个用户登录系统，包含 1. MySQL 用户表设计 2. Node.js Express 登录接口
3. JWT Token 认证。框架用 Express，ORM 用 Sequelize，密码用 bcrypt 加密。

几个立刻见效的习惯：

  • 贴具体内容：报错信息、文件片段直接粘进来，比描述"有个 bug"有效一百倍
  • Shift+Tab 切到 plan 模式：复杂任务先让它出方案，确认思路对了再动手
  • 让它反问你："在开始之前，先问我所有你需要知道的信息"，能省掉大量来回返工
  • 质疑它：/btw 可以另开一个侧问，不打断当前任务、也不污染主线上下文

权限管理

反复被同一个权限弹窗打断会很烦，可以预授权常用的安全操作： 

{
  "permissions": {
    "allow": [
      "Bash(npm run test:*)",
      "Bash(git status)",
      "Bash(git diff:*)",
      "Read(./src/**)"
    ],
    "deny": [
      "Read(./.env)",
      "Bash(rm:*)"
    ]
  }
}

用 deny 兜住绝对不能碰的东西（密钥文件、删除命令），用 allow 放行高频安全操作。剩下的才走弹窗确认。

别无脑开 auto 模式（自动批准所有工具调用）。在容器或 VM 里跑可以，在本机主力开发环境还是保留必要弹窗更稳。

常见失败模式

  • 一次给太多任务：Claude 会在几个方向上同时发散。拆开，一次一个明确目标
  • 不纠偏：发现方向不对时立刻打断。偏了之后继续加指令只会越走越远
  • Claude 停止遵循 Skill：通常是正文太长。精简到 500 行以内，把细节挪到单独文件按需读取
  • Prompt 写得太笼统：加上具体的技术栈、约束、示例，别让它猜
